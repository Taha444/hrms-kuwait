## 0) المهمة (Mission)

انت Senior Full-Stack Engineer مسؤول عن إصلاح **31 ملاحظة QA** في نظام HRMS متعدد الشركات (GUF / MUF) قبل إطلاق الـPilot.

المطلوب مش "تعديل الملاحظات واحدة واحدة" — المطلوب:

1. تفهم **السبب الجذري** لكل ملاحظة، مش العرَض الظاهر.
2. تصلّح **فئة المشكلة كلها**، مش الحالة المذكورة بس (لو نوع طلب بيعرض JSON خام، كل الأنواع لازم تتصلّح).
3. تسيب **دليل قابل للتشغيل** (test / script / خطوات) يثبت إن كل بند اتنفذ.
4. متسيبش **طرف خيط** مفتوح: كل تعديل لازم يتتبع لكل الـcall-sites والنسخ المكررة والأماكن الشبيهة.

**الهدف النهائي:** كل بند من الـ31 يبقى حالته `VERIFIED` بدليل مكتوب، ومفيش Regression في أي حاجة شغالة.

## 1) قواعد لا تُكسر (Hard Rules)

## 2) المهارات المطلوب تشغيلها (Skills)

كل مهارة دي عبارة عن **إجراء إجباري** تشغّله في وقته. اذكر اسم المهارة في الـcommit body لما تستخدمها.

### SKILL-1 · `repo-recon` — استكشاف قبل أي كود
**متى:** مرة واحدة في البداية، وقبل أي workstream جديد.
**الخطوات:**
- ارسم خريطة: طبقات الـbackend، الـORM/models، طبقة الصلاحيات، محرك الـworkflow، طبقة الـi18n، وطبقة الـjobs/cron.
- حدّد **مكان القرار** لكل موضوع: فين بيتقرر مين يعتمد؟ فين بيتحسب الغياب؟ فين بيتقري رصيد الإجازة؟
- اطلع بملف `docs/qa/ARCHITECTURE_MAP.md` فيه: الملف/الدالة المسؤولة عن كل موضوع من الـ7 workstreams.
- **ممنوع** تكتب أي سطر كود قبل ما الخريطة دي تخلص.

### SKILL-2 · `root-cause-tracer` — من العرَض للسبب
**متى:** قبل كل بند.
**الخطوات:**
1. أعِد إنتاج المشكلة (أو حدّد بالكود بالظبط ليه بتحصل) — اكتب الـtrace.
2. اسأل "ليه؟" 3 مرات على الأقل لحد ما توصل لقرار تصميمي غلط، مش سطر غلط.
3. اكتب في الـcommit body: `ROOT CAUSE:` سطر واحد واضح.
4. لو السبب الجذري بيغطي أكتر من بند — قول كده صراحة واعمل الإصلاح مرة واحدة واربطه بكل الأرقام.

> ملاحظة مهمة: بنود 1، 2، 10 غالبًا سبب جذري واحد = **آلية تحديد المُعتمِد الحالي (approver resolution)**. وبنود 6، 19، 28 غالبًا سبب واحد = **دورة حياة المستند وتاريخ الانتهاء**. وبنود 3، 4 سبب واحد = **اشتقاق الغياب من غياب السجل**. دوّر على ده قبل ما تعمل 31 إصلاح منفصل.

### SKILL-3 · `authz-workflow-guard` — حارس الصلاحيات والمسارات
**متى:** بنود 1، 2، 10، 21، 23، 29، 30، 31.
**الـChecklist الإجباري:**
- [ ] القرار "هل ده المعتمد الحالي؟" موجود في **دالة واحدة** على السيرفر، والواجهة بتستهلكها.
- [ ] الـEndpoint بترفض `403` حتى لو المستخدم نده عليها مباشرة (اختبرها بـcurl/HTTP call مش بس بالزرار).
- [ ] مفيش "super approver bypass" ضمني لأي دور (مدير الشركة/Super Admin) إلا لو ده متطلب مكتوب صراحة — ولو موجود، لازم يبقى صلاحية منفصلة مسماة وتتسجل في الـAudit.
- [ ] تركيب مراحل المسار **مشتق من محتوى الطلب** (سفر خارج الكويت؟ الفرع؟) مش قالب ثابت.
- [ ] كل صفحة/تبويب في الـsidebar عندها policy واضحة: مين يشوفها ومين لأ — والقايمة نفسها مبنية من الـpolicy.
- [ ] اعمل **مصفوفة اختبار Role × Action** واحفظها في `docs/qa/RBAC_MATRIX.md` واختبرها آليًا.

### SKILL-4 · `payroll-integrity` — سلامة الرواتب والحضور
**متى:** بنود 3، 4، 18، 24.
**الـChecklist:**
- [ ] **عدم وجود سجل حضور ≠ غياب.** لازم يبقى فيه حالة ثالثة: `غير مسجل / UNRECORDED` ومتخصمش.
- [ ] الغياب بيتحسب فقط لـ: يوم عمل رسمي، داخل فترة التوظيف، مش عطلة/إجازة معتمدة، وسياسة الحضور مفعّلة للموظف.
- [ ] فترة أي حساب متقصّة (clamped) على `[hire_date, termination_date ?? end_of_period]`.
- [ ] الـAssignment ممكن يبقى **non-payroll** (بند 18): الشخص مربوط بالشركة للصلاحيات بس، ومستبعد من الرواتب ونهاية الخدمة.
- [ ] أي قيمة صفرية غريبة (راتب 0، صافي 0) لازم تبقى إما مستبعدة أو معلّمة بسبب واضح.
- [ ] اكتب **Golden Test**: موظف تعيينه 05/08/2026 براتب 2500 — أكّد إن الخصم = المتوقع بالظبط، مش 833.333.

### SKILL-5 · `single-source-of-truth` — توحيد الأرقام
**متى:** بنود 5، 19، 20، 3.
**الـChecklist:**
- [ ] ابحث عن **كل** الأماكن اللي بتحسب نفس الرقم (grep على أسماء الحقول والدوال).
- [ ] وحّدهم في service واحدة، واحذف الحساب المكرر (متسيبش نسخة "احتياطي").
- [ ] اكتب test بيقارن نفس الرقم من نقطتين مختلفتين ويتأكد إنهم متساويين (Cross-consistency test).
- [ ] أي عداد في الـDashboard لازم يستدعي نفس الـquery اللي بتغذّي الصفحة التفصيلية.

### SKILL-6 · `doc-expiry-pipeline` — دورة حياة المستندات والإقامات
**متى:** بنود 6، 13، 14، 19، 28.
**الـPipeline المطلوب end-to-end:**
```
رفع المستند
  → OCR يستخرج (النوع، الرقم، تاريخ الإصدار، تاريخ الانتهاء)
  → تخزين التاريخ على سجل المستند/الإقامة (مع confidence flag)
  → واجهة تصحيح يدوي للمستخدم لو القراءة غلط
  → فهرسة في محرك الانتهاء/التجديد
  → Dashboard + مركز العمليات + التجديدات + التنبيهات كلهم بيقروا من نفس المصدر
  → Backfill job للمستندات المرفوعة قبل كده
```
**الـChecklist:**
- [ ] المستخدم **ما يُطلب منه** إدخال تاريخ انتهاء يدويًا كخطوة أساسية — التصحيح استثناء مش قاعدة.
- [ ] لازم `backfill` script يمشي على المستندات الموجودة ويطلّع تواريخها (ويطبع تقرير بالناجح والفاشل).
- [ ] الإصدارات: آخر إصدار = Active وهو الظاهر، والقديم متاح من زر "النسخ السابقة" مع إمكانية التحميل، ومحفوظ بتاريخه (بند 28).
- [ ] أسماء المستندات معروضة بالاسم البشري مش `form_HRMS-PR-001` (بند 14) — لازم mapping table للأنواع.

### SKILL-7 · `i18n-sweeper` — كنس النصوص التقنية
**متى:** بنود 7، 13، 14، 17، 22، 27.
**الـChecklist:**
- [ ] اعمل grep منهجي على الواجهة كلها عن: `snake_case` معروض، enum خام (`qr`, `gps`, `both`, `none`, `active`, `delegate`, `prepared`, `digest`)، مفاتيح غير مترجمة (`switch_company`)، أسماء حقول تقنية (`allowances_total`, `gross_salary`, `target_entity`).
- [ ] كل enum لازم يعدي على formatter/label map مركزي — **مش** ترجمة فردية في كل صفحة.
- [ ] أي JSON payload ظاهر للمستخدم (بند 7) يتحول لـrenderer منظم حسب نوع الطلب، مع fallback مفهوم لو النوع مش معروف.
- [ ] راجع تكرار الكلمات في المستندات المطبوعة: «شركة شركة...»، «د.ك د.ك» — السبب غالبًا القالب بيضيف بادئة والقيمة أصلاً فيها البادئة.
- [ ] النسخة الإنجليزية تستخدم الاسم الإنجليزي للشركة (بند 13).
- [ ] **Sweep إجباري:** بعد ما تصلّح، شغّل الكنس تاني وأثبت إن العدد بقى 0 — احفظ الناتج في `docs/qa/I18N_SWEEP.md`.

### SKILL-8 · `task-vs-notification` — الفرق بين المهمة والإشعار
**متى:** بنود 11، 12، 26.
**التعريف المعتمد:**
- **مهمة (Task):** مطلوب من المستخدم **إجراء**. لها owner واحد، مرتبطة بكيان (طلب/مستند)، ولها زر يفتحه، وبتتقفل تلقائيًا لما الإجراء يتم.
- **إشعار (Notification):** معلومة. مفيش `إنجاز/تجاهل`، وبتروح لمركز الإشعارات.
**الـChecklist:**
- [ ] Idempotency: إنشاء المهمة يبقى `upsert` على مفتاح `(entity_id, stage, assignee)` — عشان متتكررش.
- [ ] Auto-close: أي اعتماد/رفض يقفل المهمة المرتبطة في نفس الـtransaction.
- [ ] Backfill: اقفل المهام القديمة اليتيمة اللي إجراءها اتعمل خلاص.
- [ ] كل Task فيها deep-link للكيان.
- [ ] نص المهمة متولد من template مظبوط — مش «طلب طلب إجازة».
- [ ] أي سجل Audit لازم يحمل الفاعل + الـIP + السبب (بند 26)، بما فيهم الأحداث الآلية (تُنسب لـ`SYSTEM` بسبب واضح).

### SKILL-9 · `thread-end-sweeper` — قافل أطراف الخيوط ⭐
**متى:** بعد كل بند، إجباري. دي المهارة اللي المستخدم طالبها صراحة.
**الخطوات لكل بند:**
1. **Grep الفئة:** دوّر على نفس النمط في باقي الكود (نفس الـhelper، نفس الـcomponent، نفس نوع الـquery).
2. **اسأل 4 أسئلة:**
   - في نوع طلب/مستند/دور تاني عنده نفس المشكلة؟
   - في شركة تانية (MUF) عندها نفس المشكلة؟
   - في لغة تانية (EN) عندها نفس المشكلة؟
   - في مسار تاني للوصول لنفس الوظيفة (API مباشر، تصدير، طباعة، موبايل)؟
3. سجّل الإجابات في جدول الـ`SWEEP` في `PROGRESS.md`.
4. **البند ما يتقفلش** غير لما الأربع إجابات تبقى مغطاة.

### SKILL-10 · `verify-and-prove` — الإثبات
**متى:** قبل ما تحوّل أي بند لـ`VERIFIED`.
**المطلوب لكل بند واحد على الأقل من:**
- Automated test (المفضّل) — unit / integration / e2e حسب الطبقة.
- أو Script قابل للتشغيل بيطبع Before/After.
- أو خطوات إعادة إنتاج دقيقة + ناتج فعلي منسوخ.
**قاعدة:** الـtest لازم **يفشل قبل الإصلاح وينجح بعده** — أثبت ده (اكتب الناتج).

## 4) سجل الملاحظات (Issue Registry)

> الصيغة: `QA-XX | الخطورة | المنطقة | معيار القبول | دليل التحقق`

### 🔴 يمنع الـPilot

**QA-01 — مدير الشركة بيعتمد مراحل مش بتاعته**
- المنطقة: Approvals / Workflow · GUF · تفاصيل الطلب > مسار الطلب
- السبب المتوقع: fallback في `canApprove` بيدي مدير الشركة/Super Admin حق اعتماد أي مرحلة.
- **القبول:** كل دور يعتمد **مرحلته فقط**؛ زرار الاعتماد مخفي قبل وصول الطلب له؛ الـendpoint ترجع `403` لو اتنداهت مباشرة؛ مفيش اعتماد متسلسل بنفس الحساب.
- **الدليل:** test بيحاول اعتماد مرحلة مسؤول الفرع بحساب مدير الشركة ويتوقع 403 + مصفوفة RBAC.
- **Sweep:** كل أنواع الطلبات، الشركتين، وكل الأدوار الإدارية.

**QA-02 — مسؤول الفرع مش بيستلم الطلب الواقف على مرحلته**
- المنطقة: Approvals / Inbox · GUF · بانتظار موافقتي
- السبب المتوقع: تعارض بين المرحلة الاسمية والـapprover المُحدد فعليًا (ربط الفرع/الـassignment).
- **القبول:** الطلب يظهر في «بانتظار موافقتي» لمسؤول فرع نفس الفرع؛ يقدر يعتمد/يرفض/يرجّع؛ ورسالة «مش الموافق الحالي» تختفي.
- **الدليل:** integration test: تقديم طلب من موظف فرع X → inbox مسؤول فرع X فيه الطلب، وinbox فرع Y فاضي.
- **Sweep:** كل الأنواع اللي فيها مرحلة فرع + الشركتين. **مرتبط بـQA-01 (نفس دالة تحديد المعتمد).**

**QA-03 — عدم وجود سجل حضور بيتحول غياب وخصم**
- المنطقة: Payroll / Attendance · GUF + MUF · معاينة الراتب
- **القبول:** حالة `UNRECORDED` منفصلة عن `ABSENT`؛ الغياب يتحسب فقط بقرار/سياسة صريحة؛ مفيش خصم تلقائي على أيام بلا سجل؛ المعاينة توضح الأيام غير المسجلة كتنبيه لـHR.
- **الدليل:** Golden test على رامين (أساسي 2500) — الخصم = 0 لما مفيش سجلات، والحضور/الغياب يعكسوا الواقع.
- **Sweep:** الشركتين + كل تقارير الحضور + نهاية الخدمة لو بتستخدم نفس الحساب.

**QA-04 — غياب محسوب قبل تاريخ التعيين**
- المنطقة: Payroll / Attendance · GUF
- **القبول:** أي فترة حساب متقصّة على `hire_date`؛ الأيام قبل التعيين لا تظهر ولا تُخصم.
- **الدليل:** test لموظف تعيينه 05/08/2026 → أيام 01–04/08 مش موجودة في المراجعة ولا في الخصم.
- **Sweep:** نفس القص لازم يتطبق على `termination_date` وعلى التقارير والتصدير.

**QA-05 — رصيد الإجازات مختلف بين ملف الموظف ونهاية الخدمة (30 مقابل 92.16)**
- المنطقة: Leave / EOS · GUF
- **القبول:** مصدر واحد لحساب الرصيد؛ نهاية الخدمة تستدعيه؛ بدل الإجازات محسوب على نفس الرقم؛ لو في فرق مقصود (رصيد قابل للصرف مقابل رصيد قابل للاستخدام) لازم يتسمّى ويتعرض صراحة.
- **الدليل:** cross-consistency test: `leaveBalance(employee)` من الصفحتين لازم يتطابق.
- **Sweep:** كل مكان بيعرض رصيد إجازة (تقارير، شهادات، Dashboard).

**QA-06 — منظومة الإقامات والمستندات مش شايفة البيانات (الإقامات السارية = 0)**
- المنطقة: Documents / OCR / Renewals · GUF + MUF
- **القبول:** الـpipeline في SKILL-6 شغال كامل؛ OCR يستخرج تاريخ الانتهاء تلقائيًا؛ التاريخ يتخزن؛ Dashboard + مركز العمليات + التجديدات + التنبيهات كلهم يقروا من نفس المصدر؛ backfill للمستندات القديمة؛ تصحيح يدوي متاح.
- **الدليل:** رفع مستند تجريبي → التاريخ اتقري واتخزن → العدادات اتحدثت → التنبيه اتولد. + تقرير backfill.
- **Sweep:** إقامة / إذن عمل / جواز / بطاقة / مستندات الشركة، والشركتين.

**QA-10 — مرحلة المندوب بتظهر في الإجازة العادية بدون سفر**
- المنطقة: Workflow · GUF + MUF
- **القبول:** مراحل المسار مشتقة من محتوى الطلب؛ مرحلة المندوب وإذن مغادرة البلاد تظهر **فقط** مع سفر خارج الكويت.
- **الدليل:** test لطلبين (بسفر / بدون) ومقارنة المراحل الناتجة.
- **Sweep:** كل شرط مسار مشابه (مثلاً مراحل مالية تظهر بشرط مبلغ معين).

### 🟠 مهم

**QA-07 — تفاصيل الطلب ظاهرة كـJSON خام**
- **القبول:** renderer لكل نوع طلب يعرض: نوع الإجازة (سنوية)، من/إلى بصيغة `DD/MM/YYYY`، عدد الأيام، السبب. Fallback مفهوم للأنواع غير المعروفة (label:value مترجمة، مش JSON).
- **الدليل:** لقطة/test لكل نوع طلب متاح. **Sweep: كل الأنواع + التصدير + الطباعة.**

**QA-08 — «استبدال التوقيع» بيرجع: نوع الطلب REQSIG غير متاح لحسابك**
- **القبول:** نوع الطلب مسجّل ومتاح للموظف؛ الزرار يفتح طلب تغيير توقيع بسبب؛ يروح لـHR؛ التوقيع القديم يفضل نشط لحد الموافقة.
- **الدليل:** e2e من الموظف لحد اعتماد HR. **Sweep: كل أنواع الطلبات المعرّفة — تأكد مفيش نوع تاني غير مربوط بأي دور.**

**QA-09 — أنواع طلبات مكررة (شهادة راتب / شهادة راتب V1.3 / سلفة / قرض / سلفة أو قرض)**
- **القبول:** كل خدمة تظهر مرة واحدة بالاسم النهائي؛ الأنواع القديمة `deprecated` — تفضل للطلبات التاريخية وما تظهرش في التقديم الجديد.
- **الدليل:** قائمة الأنواع المتاحة للتقديم = القائمة المعتمدة بالظبط + الطلبات القديمة لسه بتفتح صح.

**QA-11 — مهام مكررة وبتفضل مفتوحة بعد انتهاء الإجراء**
- **القبول:** SKILL-8 كامل: مهمة واحدة لكل إجراء، مرتبطة بالطلب، بلينك، تتقفل تلقائيًا، النص مظبوط («طلب إجازة» مش «طلب طلب إجازة»)، ومستوى الأهمية منطقي.
- **الدليل:** test إنشاء طلب مرتين متتاليتين → مهمة واحدة؛ واعتماد → المهمة اتقفلت. + backfill للمهام اليتيمة.

**QA-12 — الإشعارات ظاهرة كمهام بأزرار إنجاز/تجاهل**
- **القبول:** فصل واضح Task vs Notification حسب SKILL-8؛ تحديثات الحالة تروح للإشعارات.
- **الدليل:** تصنيف كل نوع حدث في جدول + test.

**QA-13 — أسماء حقول تقنية وأخطاء في المستندات المطبوعة**
- **القبول:** لا `allowances_total`/`gross_salary`/`target_entity` ظاهرة؛ لا تكرار «شركة شركة» ولا «د.ك د.ك»؛ النسخة EN تستخدم الاسم الإنجليزي؛ لا placeholders فاضية مطبوعة؛ `Employee ID` = الرقم الوظيفي مش الـinternal id.
- **الدليل:** توليد كل قالب ومراجعة الناتج. **Sweep: كل الصيغ والنماذج بالعربي والإنجليزي.**

**QA-14 — نوع المستند ككود + مستندات مكررة بنفس الاسم والنسخة**
- **القبول:** mapping من الكود للاسم البشري؛ التكرار يتحل بعرض التاريخ/الإصدار/الجهة عشان المستخدم يفرّق، أو بدمج المكرر الحقيقي.
- **الدليل:** قائمة أنواع المستندات كلها معروضة بأسماء مفهومة.

**QA-15 — الموظف الجديد ما بيظهرش غير بعد Refresh**
- **القبول:** القائمة والعداد يتحدثوا فورًا بعد الحفظ (invalidate cache / refetch).
- **الدليل:** e2e إضافة موظف → ظهر من غير reload. **Sweep: كل الشاشات اللي فيها إنشاء + رجوع لقائمة.**

**QA-16 — أرشيف الشركة فاضي بدون رسالة لما «كل الشركات» مختارة**
- **القبول:** إما عرض مناسب أو رسالة صريحة «اختر شركة لعرض أرشيفها».
- **Sweep:** كل الصفحات اللي بتحتاج شركة محددة لازم يبقى عندها نفس الـEmpty State.

**QA-18 — محمد فاروق بيدخل رواتب الشركة الثانية براتب 0**
- **القبول:** `assignment` من نوع non-payroll (وصول/صلاحية بس)؛ مستبعد من الرواتب ونهاية الخدمة؛ لسه شغال كمندوب في الشركتين.
- **الدليل:** معاينة رواتب MUF مفيهاش السطر ده + المندوب لسه بيشتغل عادي.

**QA-19 — تناقض التراخيص: 76%/24% في Dashboard مقابل صفر منتهي في مركز العمليات**
- **القبول:** العدادان من نفس مصدر البيانات والتواريخ (مرتبط بـQA-06).
- **الدليل:** cross-consistency test بين الـDashboard والصفحة التفصيلية.

**QA-20 — المهام الحكومية = 2 في Dashboard و«لا توجد بيانات» في الفلتر**
- **القبول:** العداد والفلتر يستخدموا نفس الـquery/الفلتر بالظبط.
- **الدليل:** test بيقارن `count()` بـ`length(list())`. **Sweep: كل عدادات الـDashboard.**

**QA-21 — صاحب الشركات بيشوف عدد الموظفين بدون صفحة موظفين**
- **القبول:** صفحة الموظفون متاحة له، بتعرض موظفي شركاته حسب الشركة المختارة، بصلاحيات قراءة مناسبة.
- **الدليل:** RBAC matrix + e2e.

**QA-28 — النسخ القديمة من المستندات مش قابلة للوصول/التحميل**
- **القبول:** آخر إصدار Active هو الظاهر؛ زر «النسخ السابقة» داخل المستند؛ كل إصدار قديم قابل للعرض والتحميل؛ محفوظ بتاريخه؛ الإصدار الجديد ما بيمسحش القديم.
- **الدليل:** رفع v2 → v1 لسه موجود وقابل للتحميل بنفس المحتوى.

**QA-29 — صفحة الروابط الحكومية ظاهرة لغير المندوب**
- **القبول:** الصفحة للمندوب (PRO) فقط — sidebar + route guard + API.
- **الدليل:** RBAC matrix لكل الأدوار.

**QA-30 — 2FA مش مفعّل فعليًا لـHR/المندوب/مدير الشركة**
- **القبول:** إعداد أول مرة (enrollment) + طلب التحقق فعليًا في كل تسجيل دخول تالي؛ recovery codes؛ مش مجرد صفحة إعداد.
- **الدليل:** e2e تسجيل دخول ثاني بيطلب الكود ويرفض الغلط.

**QA-31 — Session timeout للحسابات الإدارية**
- **القبول:** خمول ~10 دقائق بدون تفاعل → تسجيل خروج تلقائي ورجوع لشاشة الدخول (idle timeout مطبق على الـtoken/session مش الواجهة بس).
- **الدليل:** test بمحاكاة الخمول → الـAPI ترفض التوكن.
