# HRMS Bug Workflow — من الاكتشاف إلى الإغلاق

## القاعدة الحاكمة
**لا تصلح أثناء جولة الاختبار.** سجّل واستمر.
الإصلاح أثناء الاختبار يفسد خط الأساس: تنسى ما اختبرته، وتخلط أعطالا كان يمكن أن تكشف جذرا واحدا.

الترتيب: **جولة كاملة → تحليل → إصلاح → إعادة اختبار.**

## 1. التسجيل — ستة حقول إجبارية
```
المعرّف:     BUG-xxx أو معرّف الرحلة التي كشفته
البيئة:      الرابط · Build · Commit · الشركة (GUF/MUF) · الحساب والدور
الخطوات:     مرقّمة، قابلة للتكرار حرفيا من صفر
المتوقع:     ما كان يجب أن يحدث
الحادث:      ما حدث فعلا — كود الحالة، نص الخطأ، لقطة، جسم الرد
الخطورة:     blocker (يمنع التسليم) · high · medium · low
```

**بلا خطوات قابلة للتكرار، البلاغ ليس بلاغا.** لو لم تستطع تكراره مرتين، اكتب ذلك صراحة.

## 2. الخطورة — معيار واحد
| الدرجة | المعيار |
|---|---|
| `blocker` | ثغرة صلاحيات أو خصوصية · فقد بيانات · حساب مالي خاطئ · مسار أساسي لا يعمل · بيانات دخول تجريبية شغّالة |
| `high` | ميزة أساسية مكسورة لها التفاف · تناقض بيانات بين شاشتين · أثر تشغيلي لا يُطبَّق |
| `medium` | إزعاج تشغيلي · نص خاطئ في مستند · عداد غير مطابق |
| `low` | تجميل · قيمة خام في الواجهة · حالة فارغة بلا رسالة |

**تسريب بيانات = blocker دائما**، مهما بدا صغيرا.

## 3. تحليل الجذر — قبل أي كود
أربعة أسئلة:
1. **أين مصدر الحقيقة** لهذا السلوك؟ (ملف ودالة محددان، لا تخمين)
2. **كم مكان آخر** يقرأ من نفس المصدر أو يكرر نفس المنطق؟
3. هل الأعطال الأخرى في هذه الجولة **تشترك في نفس الجذر**؟
4. لماذا لم يُكتشف قبل الآن؟ (يكشف فجوة في التغطية)

الجذور المتكررة في هذا النظام تحديدا:
```
مصدر صلاحيات غير موحّد بين Menu/Route/API/Button
كل شاشة تحسب بنفسها بدل مصدر بيانات واحد
غياب current_assignee حقيقي في المهمة
نموذج عام واحد لكل الطلبات
غياب employee_id في المستخدم
خلط Preview بالإصدار
```

**اعرض قائمة الأعطال التي سيغلقها إصلاحك قبل أن تبدأ الكتابة.**

## 4. الإصلاح
- في **الجذر** لا في العرَض.
- على **الخادم** — أي فحص في الواجهة يحتاج مقابلا في الـ API.
- **مع اختبار آلي** يغطي الحالة ويمنع عودتها.
- بأصغر تغيير يحل المشكلة — **لا Scope جديد ولا تحسينات جانبية**.

### ما يبطل الإصلاح فورا
- إخفاء عنصر بـ CSS لحل مشكلة صلاحية أو خصوصية
- `catch` أو ابتلاع خطأ الخادم بدل معالجته
- تعديل الاختبار ليمر بدل إصلاح الكود
- إصلاح على شركة واحدة

## 5. الكنس — الأبعاد الستة
بعد أي إصلاح، اذكر ما فعلته في كل بُعد:
| البُعد | التغطية |
|---|---|
| الأدوار | Employee · BranchSupervisor · Manager · HR · Accountant · PRO · Owner · SuperAdmin |
| الشركات | GUF **و** MUF |
| مسارات الوصول | القائمة · الرابط المباشر · الـ API · Storage · Deep link · Back · Reload |
| اللغة | عربي RTL · إنجليزي LTR |
| الحالات | Loading · Empty · Error · Unauthorized · Success |
| الطبقات | UI · API · Storage · DB · Export · PDF · Notification payload |

## 6. الاختبار الانحداري
بعد الإصلاح، أعد تشغيل:
- الرحلة التي كشفت العطل
- **كل رحلة تشترك في نفس الجذر** — هنا يظهر الكسر الجانبي
- كل رحلات الـ blocker

```bash
python3 .claude/hrms/scripts/testrun.py --result <ID> pass --note "أُصلح في <commit> · اختبار <ملف>"
bash .claude/hrms/scripts/smoke.sh
bash .claude/hrms/scripts/rbac-probe.sh
```

## 7. الإغلاق
عطل يُغلق فقط عندما:
- [ ] فُهم جذره ووُثِّق
- [ ] أُصلح في الجذر
- [ ] له اختبار آلي يمنع عودته
- [ ] الأبعاد الستة مكنوسة
- [ ] الرحلة الأصلية أُعيد تشغيلها ونجحت
- [ ] الرحلات الشقيقة لم تنكسر

## 8. الأعطال التي لا تُصلح
بعضها ليس عطلا برمجيا:
- **يحتاج قرار عمل** (حد مالي، سياسة إجازة، من يعتمد ماذا) → سجّله `blocked` واطلب القرار صراحة
- **يحتاج اعتماد قانوني** (صياغة إنذار أو خصم أو مخالصة) → المهندس ينفّذ البنية، والنص يبقى معلّقا
- **قرار مقصود** (وجود المندوب في شركتين) → وثّقه كسلوك مقصود حتى لا يُبلَّغ مرة أخرى

**لا تخترع قرار عمل من عندك.** اسأل.
