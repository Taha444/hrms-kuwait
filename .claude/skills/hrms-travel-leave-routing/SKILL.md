# Package 9 — إجازة السفر

## P9-32 — التناقض

### الدليل
Request 13 يحتوي وجهة (مصر) وسببا واضحا أنه سفر، لكنه بقي `WF-001` وليس `WF-002`.

### تحقّق أولا — بند `V-C`
> **لم نعتبر routing engine مكسورا بشكل مؤكد لأن `travel_required=true` لم يُثبَت.**

افحص قيمة `travel_required` في السجل تحديدا:
```sql
SELECT id, type_code, workflow_code, payload->>'travel_required',
       payload->>'destination' FROM requests WHERE id = 13;
```

**عطلان مختلفان تماما:**
| الحالة | التشخيص | الإصلاح |
|---|---|---|
| `true` ولم يدخل WF-002 | **عطل routing مؤكد** | محرك التوجيه لا يقرأ الحقل |
| `false` رغم بيانات السفر | **عطل form/validation** | الحقل لم يُحفظ أو النموذج سمح بالتناقض |

**لا تصلح قبل معرفة أيهما.** الإصلاح مختلف كليا.

## المطلوب — النموذج يسأل صراحة
```
هل الإجازة تتضمن سفرا خارج الكويت؟

نعم  →  travel fields تصبح required
      →  destination
      →  routing حسب قاعدة العمل المعتمدة للسفر

لا   →  Normal Leave
```

> **ممنوع وجود Travel-specific data بينما الطلب الداخلي ما زال Normal بسبب checkbox منسية.**

**التحقق على الخادم:** لو وصل `destination` أو أي حقل سفر بينما `travel_required=false` → **ارفض الطلب** واطلب التوضيح. التناقض لا يُحفظ.

## قرار عمل — لا تقرره من عندك
> **لا تقرر من عندك إن كل سفر لازم PRO.**

السؤال المطلوب تثبيته أولا:
```
متى تحتاج Travel Leave إلى PRO / exit / government stage؟
```
احتمالات: كل سفر؟ · السفر الذي يتطلب إذن مغادرة؟ · حسب الجنسية أو نوع الإقامة؟ · حسب المدة؟

**اسأل العميل واحصل على القاعدة مكتوبة قبل التنفيذ.**

**قاعدة حماية 11:** Normal Leave بدون سفر **لا يدخل PRO** — هذه مثبتة ولا نقاش فيها.

## القبول
`DOD-02`: السفر مُختار بوضوح → التوجيه الصحيح → مرحلة PRO/حكومية **حسب قاعدة العمل فقط** → لا غموض.
