# HRMS Delivery Package — متطلبات التسليم لشركة

## الأداة
```bash
python3 .claude/hrms/scripts/delivery.py            # حالة الحزمة
python3 .claude/hrms/scripts/delivery.py --pending  # الناقص
python3 .claude/hrms/scripts/delivery.py --set DLV-03 done --note "..."
python3 .claude/hrms/scripts/delivery.py --report   # تقرير الجاهزية
```

## المبدأ
التسليم ليس «الموقع شغّال». التسليم هو أن **الشركة تستطيع تشغيل النظام والاعتماد عليه واسترجاعه دون وجودك**.
معيار بسيط: لو اختفيت غدا، هل يستطيع فريق العميل التعامل مع النظام؟ كل بند ناقص في هذه القائمة هو إجابة "لا".

## 1. البوابة الأولى — لا تسليم قبلها
- [ ] لا يوجد أي blocker مفتوح
- [ ] كل رحلات الـ blocker في كتالوج الاختبار نجحت على **الشركتين**
- [ ] الفحص الأمني مكتمل بلا بند فاشل
- [ ] فحوص سلامة البيانات نظيفة
- [ ] النسخة المُختبَرة **هي نفسها** النسخة المُسلَّمة (نفس Commit)

**تسليم بـ blocker مفتوح ليس تسليما — هو نقل المشكلة للعميل.**

## 2. هوية النسخة والنشر
- [ ] `Version` · `Full Commit SHA` · `Built At` · `Deployed At` · `Environment` · `Migration Version` · `Feature Flags` — ظاهرة في النظام
- [ ] لا يظهر `Development` على رابط التسليم
- [ ] `System Health`: Data و Migrations = PASS
- [ ] Service Worker/PWA يُحدَّث ولا يُبقي المستخدم على بناء قديم
- [ ] وثيقة إصدار (Release Notes) بما تم وما لم يتم

## 3. البيئة والبنية
- [ ] بيئة العميل **منفصلة تماما** عن Staging
- [ ] نطاق (Domain) نهائي وشهادة SSL صالحة + تنبيه قبل انتهائها
- [ ] موارد الخادم موثّقة (CPU/RAM/Disk) وتقدير للنمو
- [ ] من يملك الاستضافة والنطاق والشهادة؟ **وثّق ذلك صراحة** — أكثر نقطة تسبب نزاعا بعد التسليم
- [ ] بيانات الشركة (شعار، اسم قانوني، رخصة، عنوان، ختم) مركّبة ومعتمدة من المالك

## 4. النسخ الاحتياطي والاسترجاع — الأهم بعد الأمان
- [ ] نسخ احتياطي **آلي مجدول** لقاعدة البيانات والملفات
- [ ] **اختبار استرجاع فعلي مُنفَّذ وموثّق** — نسخة احتياطية غير مُختبَرة ليست نسخة احتياطية
- [ ] مدة الاحتفاظ محددة ومتفق عليها
- [ ] نسخة خارج الخادم (off-site)
- [ ] `RTO` و `RPO` مكتوبان: كم ساعة توقف مقبولة؟ وكم بيانات يُقبل فقدها؟
- [ ] إجراء الاسترجاع مكتوب **خطوة بخطوة** ليستطيع غير كاتب الكود تنفيذه

## 5. المراقبة والتشغيل
- [ ] `Health Checks` · `Monitoring` · `Error Tracking` · `Structured Logs`
- [ ] تنبيهات عند فشل: Daily Scan · Notification · PDF Generation · Backup · Payroll Job
- [ ] إلى **من** تصل التنبيهات؟ (بريد أو قناة محددة، لا "الفريق")
- [ ] `Rate Limits` مفعّلة
- [ ] `Rollback Plan` مكتوب و **مُجرَّب**
- [ ] `Smoke Test` بعد النشر — يُفضَّل آلي

## 6. الحسابات والمفاتيح — تسليم آمن
- [ ] حساب Super Admin الداخلي **لا يُسلَّم** — يُنشأ حساب مالك للعميل
- [ ] حسابات شخصية لكل مسؤول، **لا حساب مشترك**
- [ ] إجبار تغيير كلمة السر عند أول دخول
- [ ] كل بيانات الدخول التجريبية معطّلة
- [ ] مفاتيح Kiosk مُدوَّرة
- [ ] مفاتيح الأنظمة الخارجية (بريد، SMS، تخزين) مُدوَّرة ومملوكة للعميل

**قاعدة صارمة:** بيانات الدخول تُسلَّم عبر **قناة آمنة يديرها العميل** (مدير كلمات سر أو تسليم شخصي). ممنوع إرسالها في بريد أو محادثة أو مستند مشترك. وثّق **من استلم ماذا ومتى** بتوقيع.

## 7. البيانات
- [ ] بيانات QA **منظّفة أو معزولة** — لا تختلط ببيانات العميل
- [ ] `Reset Demo Data` وأدوات الاختبار **معطّلة في بيئة العميل**
- [ ] الشهادة التجريبية في ملف الموظف محذوفة
- [ ] الشركة المكررة محذوفة
- [ ] البيانات الأولية محمّلة: الشركات · الفروع · الأقسام · الموظفون · المستخدمون · سياسات الحضور
- [ ] خطة الترحيل من النظام القديم مُنفَّذة وموثّقة (إن وُجد)

## 8. الوثائق
| الوثيقة | لمن |
|---|---|
| دليل المستخدم لكل دور (عربي/إنجليزي) | مستخدمو النظام |
| دليل المسؤول: إعدادات · صلاحيات · قوالب · سياسات | HR/Admin |
| دليل التشغيل (Runbook): نشر · نسخ احتياطي · استرجاع · تنبيهات شائعة | فريق تقني |
| مخطط قاعدة البيانات ووصف الجداول الأساسية | فريق تقني |
| توثيق الـ API (إن كان سيُستخدم) | فريق تقني |
| مصفوفة الصلاحيات: دور × شاشة × إجراء | HR/Admin |
| دفتر السياسات: الحدود المالية · مدد الإجازات · قواعد الاعتماد | إدارة الأعمال |
| قائمة القرارات المعلّقة | إدارة الأعمال |

**دليل المستخدم بالعربي إلزامي** — النظام عربي وبعض المستخدمين لا يقرؤون الإنجليزية.

## 9. التدريب
- [ ] `Tutorial` داخل النظام لكل دور، عربي وإنجليزي، 5-8 خطوات، مع Replay
- [ ] جلسة تدريب لكل مجموعة أدوار
- [ ] تسجيل الجلسات إن أمكن
- [ ] صفحة مساعدة أو FAQ مختصرة
- [ ] `Empty States` تشرح الخطوة التالية بدل الفراغ

## 10. الدعم والضمان — يُكتب لا يُفترض
هذه البنود سبب معظم النزاعات بعد التسليم. **اتفق عليها كتابة قبل التسليم:**
- [ ] مدة الضمان وما يشمله (إصلاح عيوب) وما لا يشمله (مزايا جديدة)
- [ ] تعريف واضح لـ «عيب» مقابل «طلب تغيير»
- [ ] قنوات الدعم وأوقاته
- [ ] أزمنة الاستجابة حسب الخطورة
- [ ] آلية طلبات التغيير وتسعيرها
- [ ] ملكية الكود والبيانات — **صريحة ومكتوبة**
- [ ] ما يحدث عند انتهاء العلاقة: تصدير البيانات · تسليم الكود · مدة انتقالية

**تنبيه:** هذه بنود تعاقدية. أنا أساعد في تجهيز قائمتها ومحتواها التقني، لكن **الصياغة القانونية والتوقيع يحتاجان محاميا** — خصوصا في الكويت حيث تحكم علاقات العمل قوانين محلية. لا تعتمد على صياغة مولّدة كعقد.

## 11. الامتثال القانوني — بوابة خارجية
النظام يُصدر مستندات لها أثر قانوني (إنذار، خصم، مخالصة، نهاية خدمة). **لا تُفعَّل نصوصها كنهائية قبل:**
- [ ] اعتماد مالك الشركة لشكل الورقة الرسمية وبياناتها
- [ ] اعتماد HR Owner لحقول كل مستند
- [ ] **مراجعة محامٍ كويتي** لصياغات: الإنذار · التحقيق · الخصم · السلفة · الاستقالة · نهاية الخدمة · المخالصة · التظلم
- [ ] اعتماد Finance لمصادر الأرقام وقواعد التقريب
- [ ] اعتماد المخوّلين بالتوقيع لنطاق كل منهم

المهندس ينفّذ **البنية والحقول**؛ تفعيل النص مشروط بتوقيع المختص. سلّم النظام مع هذه البنود معلّقة صراحة إن لم تكتمل — ووثّق ذلك في محضر التسليم.

## 12. محضر التسليم
وثيقة موقّعة من الطرفين تحتوي:
```
التاريخ · النسخة · Commit SHA · Migration Version · الرابط
ما سُلِّم (مرجع لقائمة الحزمة)
ما لم يكتمل ولماذا وموعده
البنود المعلّقة على قرار العميل أو اعتماد قانوني
من استلم أي حسابات ومفاتيح ومتى
شروط الضمان والدعم
تحفظات العميل إن وُجدت
```

## قبل تحديد موعد التسليم
شغّل `--pending` واعرض الناقص. **لا تحدد موعدا وأنت لا تعرف حجم الناقص** — هذا أكثر سبب لتسليم متعثر.
