# HRMS Identity & Access (عنقود ACCESS — 15 بندا، 7 منها blocker)

## 1. ربط User بـ Employee — `ACCESS-01`
العطل الأصلي: مستخدم أُنشئ بدور Employee و `employee_id` فارغ. دخل وغيّر كلمة السر، لكن My Profile يرجع 404 والحضور لا يعمل، بينما سجل الموظف موجود في الحضور والرواتب.

القواعد:
- إنشاء المستخدم والربط **Transaction واحدة**.
- **ممنوع تفعيل Employee User و `employee_id` فارغ** — قيد على مستوى قاعدة البيانات لا تحقق في الكود فقط.
- الربط: اختيار Employee صريح من نفس الشركة، أو تلقائي بالمدني مع company context **بشرط عدم الالتباس**.
- فشل الربط → لا حساب Active.
- **معالجة الحسابات الحالية الموجودة بلا `employee_id`** — هذه خطوة ترحيل منفصلة، لا تنساها.
- Audit للإنشاء والتغيير.

اختبر المسار كاملا: `Company > Branch > Department > Employee > User > Link > Login > Change Password > My Profile > Attendance > Requests`.

## 2. الدور الإداري لا يلغي صفة الموظف — `ACCESS-02` و `CAT-05`
هذه أهم قاعدة في العنقود، ومكررة في ثلاثة مصادر:

> كل حساب مربوط بـ Employee يرى **الاثنين معا**: خدماته الشخصية (My Profile, My Attendance, My Requests) **و** إجراءات دوره (Work Actions, Approvals, Tasks).

- الفصل يكون **في الواجهة** بين «طلباتي» و«إجراءات العمل» — لا بحجب أحدهما.
- HR يقدر يقدم إجازة. Manager يقدر يطلب شهادة راتب. PRO يقدر يطلب تصحيح حضور.
- الإجراءات الداخلية (إصدار إنذار، تشغيل راتب، تكليف مندوب، اعتماد مصروف) **لا تظهر كطلبات شخصية**.
- المستخدم الإداري **غير المربوط** بـ Employee: لا خدمات ذاتية إطلاقا.
- عند تقديم طلب شخصي: **منع الاعتماد الذاتي** وتحويله للموافق البديل أو الأعلى وفق الـ Workflow.

## 3. مصدر صلاحيات واحد — `ACCESS-12`
العطل: توجد صلاحية في API بلا مسار ظاهر، ورابط ظاهر بلا صلاحية.

القاعدة: **Menu و Route و Button و API يقرأون من نفس Permission Source.**
الحماية تشمل سبع طبقات: `Menu · Route · API · Action · Field · File · Export`.

النطاقات:
| الدور | النطاق |
|---|---|
| Owner | الشركات المسندة له |
| Manager / HR | داخل الشركة |
| Branch Supervisor | داخل الفروع المسندة |
| PRO | داخل نطاقه المسند |
| Employee | نفسه فقط |
| Accountant | الحقول المالية المطلوبة فقط |
| Super Admin | حسب صلاحياته، وليس موافقا افتراضيا |

البيانات الحساسة: `Salary · Civil ID · Passport · IBAN · Documents · EOS · Grievances · Investigations`.
المحاولة غير المصرح بها **ترفض بدون إرجاع بيانات في جسم الرد**.

## 4. القيود المحددة المطلوبة الآن
- **Accountant** (`ACCESS-03`): يُمنع من Passport و Civil ID و Contract و Documents و Leave Management و Warnings و EOS. المنع في **UI و API و Storage endpoint** معا — الثلاثة، لا واحدا.
- **PRO** (`ACCESS-04`): يُمنع من إنشاء الموظف ومن Basic Salary و Hire Date و Contract fields. يرى فقط ما يلزم للإقامات والمعاملات الحكومية.
- **Branch Supervisor** (`ACCESS-06`): تبويب EOS لا يظهر أصلا بدل أن يفتح فارغا.
- **Owner** (`ACCESS-07`): رابط الموظفين يظهر في Sidebar (الصفحة والـ Route والنطاق سليمة بالفعل).
- **الروابط الحكومية** (`ACCESS-05`): لـ PRO فقط — **تحقق أولا، المصدر متناقض**.

## 5. الجلسات والمصادقة
- **2FA** (`ACCESS-08` — blocker): الخوارزمية سليمة، المشكلة **فرق توقيت الخادم ~111 ثانية**. ابدأ بضبط NTP، ثم تحقق أن 2FA مطبّق فعليا في مسار تسجيل الدخول لا كصفحة إعداد. الأدوار: HR و PRO و Manager. **أزل 2FA من QA Employee Test** — كان لأغراض الاختبار فقط.
- **Auto Logout** (`ACCESS-09`): لا يوجد Idle mechanism فعلي — الجلسة تعتمد على Token Expiry. المطلوب خمول ~10 دقائق للأدوار الثلاثة فقط.
- **الحسابات التجريبية** (`ACCESS-10`): تعطيل كل كلمات السر التجريبية، إلغاء الحساب المشترك، حسابات شخصية، إجبار تغيير كلمة السر أول Login. حساب Super Admin الحالي **لن يُسلّم للعميل**.
- **Rate Limit و Lockout** (`ACCESS-11`) + إنهاء Sessions بعد تغيير كلمة السر أو التعطيل.
- **ملاحظة**: منع دخول المستخدم المعطل **نجح في الاختبار** — حافظ عليه ولا تكسره.

## 6. حالات الواجهة — `ACCESS-14` و `ACCESS-15`
- خارج النطاق → **Unauthorized أو Not Found**، لا Loading دائم.
- Quick Actions: لا Payroll للـ Manager الممنوع · لا EOS للـ Accountant · نص 2FA حسب الدور الحقيقي.

## التحقق
بعد أي إصلاح هنا، طبّق `hrms-verification-protocol` — وبالذات بُعد **مسارات الوصول** (رابط مباشر + API مباشر + Storage) وبُعد **الشركتين**.
