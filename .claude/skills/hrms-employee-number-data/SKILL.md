# Package 7 — رقم الموظف وسلامة البيانات

## P7-29 — أرقام موظفين ناقصة

### الوضع
يوجد موظفون حقيقيون بـ `employee_no = null`، وعدد كبير من السجلات القديمة بلا رقم، في GUF و MUF.

**النظام الحالي يولّد الرقم بالشكل المعتمد:**
```
Company abbreviation + Branch code + sequence
مثال: GUF-GUF2-00001
```

### المطلوب
> **بعد التأكد من السجلات الحقيقية**، شغّل safe backfill للموظفين بلا رقم.

«بعد التأكد» مهمة: افصل الموظفين الحقيقيين عن سجلات الاختبار قبل التعبئة. تعبئة أرقام لسجلات وهمية تستهلك تسلسلات لن تُستخدم — **والرقم لا يُعاد استخدامه**.

### القواعد
```
unique · immutable · concurrency-safe · never reused
```
**concurrency-safe** يعني تسلسل أو قفل على مستوى قاعدة البيانات — لا `count()+1`.

### يظهر في
```
Lists · Profile · Search · Reports · Templates · Official documents
```
> **لا تستخدم DB ID بدل employee_no في أي مستند رسمي.**

### خطة التعبئة
```
1. احصر: SELECT id, full_name, company_id, branch_id FROM employees WHERE employee_no IS NULL;
2. صنّف: حقيقي أم بيانات اختبار
3. رتّب بالأقدم (created_at) ليكون التسلسل منطقيا
4. عبّئ داخل transaction بقفل على التسلسل
5. تحقق من التفرّد بعد التعبئة
6. افحص المستندات التي صدرت سابقا بـDB ID — هل تحتاج إعادة إصدار؟
```

## P7-30 — بيانات الاختبار ليست عطلا في المنتج (قاعدة حماية)

> **لا تصلح بيانات اختبار مختلطة بتغيير business logic.**

صنّفها **Data Cleanup فقط**: أسماء فروع/شركات مختلطة · departments/shifts فارغة · سجلات قديمة.

### الاستثناء المهم
لو نقص البيانات يجعل ميزة حقيقية **مستحيلة**، الواجهة تعرض **Setup Required مفهوم** بدل form مكسور:

```
REQSHIFT يحتاج Shift ولا توجد Shifts
  ✗  form مكسور أو خطأ عام
  ✓  "لا توجد ورديات مُعرّفة — قم بتعريف الورديات أولا"  (للدور المناسب)
```

### تحقّق أولا — بند `V-F`
REQSHIFT: **إعداد ناقص أم workflow غير قابل للاستخدام؟** افحص قبل الحكم.
لو إعداد ناقص → الحل شاشة Setup Required.
لو الـ workflow نفسه مكسور → عطل يُسجَّل.

طبّق نفس التمييز على كل ميزة تعتمد على إعداد مسبق: الورديات · سياسات الحضور · المخوّلين بالتوقيع · قواعد السياسة.
