# HRMS Verification Protocol

## لماذا هذا السكيل موجود
معظم بنود القائمة الحالية تحمل كلمة **«لسه»** — أي أنها أُصلحت مرة وعادت. السبب المتكرر: الإصلاح تم في **مكان واحد** بينما نفس المنطق مكرر في أماكن أخرى.

## الدورة الإلزامية لكل بند

### 1. أعِد إنتاج العطل أولا
**ممنوع الإصلاح قبل رؤية العطل بعينك.** استخدم خطوات `verify` في السجل.
إن لم تستطع إعادة إنتاجه:
- ربما أُصلح بالفعل → `--set <ID> verified` مع تسجيل ما اختبرته
- ربما شروط الاختبار مختلفة → اسأل عن الحساب والشركة والبيانات الدقيقة
- **لا تصلح شيئا لم تره** — ستكسر ما يعمل

### 2. حدد الجذر لا العرَض
اسأل قبل الكتابة:
- أين مصدر الحقيقة لهذا السلوك؟
- كم مكان آخر يقرأ من نفس المصدر أو يكرر نفس المنطق؟
- هل العرَض ظاهر في شاشة واحدة لأن الشاشات الأخرى لا تُستخدم بعد؟

مثال حي من السجل: `ATT-04` — الغياب قبل التعيين أُصلح في Payroll Preview وبقي في Attendance Review. الجذر واحد ويجب إصلاحه في مصدر البيانات المشترك.

### 3. الكنس بعد الإصلاح — الأبعاد الستة
بعد أي إصلاح، اسأل عن كل بُعد صراحة وسجّل الإجابة:

| البُعد | السؤال |
|---|---|
| **الأدوار** | Employee · Branch Supervisor · Manager · HR · Accountant · PRO · Owner · Super Admin — هل السلوك صحيح لكل واحد؟ |
| **الشركات** | GUF و MUF — هل الإصلاح يعمل في الاثنتين؟ هل كسر إحداهما؟ |
| **مسارات الوصول** | القائمة · الرابط المباشر · الـ API مباشرة · Deep link · Back button · إعادة تحميل |
| **اللغة** | عربي RTL و إنجليزي LTR — النصوص والأرقام والتواريخ والعملة |
| **الحالات** | Loading · Empty · Error · Unauthorized · Success — لا خلط بينها |
| **الطبقات** | UI · API · Storage · Database · Export · PDF · Notification payload |

**البُعد الأهم في هذا المشروع: الشركتان.** بلاغ `API-01` صريح: نفس الـ endpoint يعمل على MUF ويفشل على GUF. أي إصلاح يُختبر على الاثنتين.

### 4. أثبت أن الأثر التشغيلي وقع
كثير من البنود عن **طلب يصل Completed بلا أثر**. بعد أي إصلاح في مسار طلب، تحقق فعليا من:
- سجل الحضور تغيّر؟
- رصيد الإجازة خُصم؟
- قيد الراتب أُنشئ؟
- المستند صدر بملف حقيقي؟
- المهمة أُغلقت؟
- الإشعار وصل؟

**لا تكتفِ بحالة الطلب.** الحالة تتغير بسطر واحد؛ الأثر لا.

### 5. تحقق أن الفحص على الخادم
لكل صلاحية أو تحقق أضفته في الواجهة:
```
افتح الرابط مباشرة بمستخدم غير مخوّل  →  يجب 403
اضرب الـ API مباشرة                    →  يجب 403
اضرب الـ Storage endpoint مباشرة        →  يجب 403
```
والاستجابة **لا تسرّب بيانات في جسم الخطأ**.

### 6. سجّل ولا تدّعِ
```bash
python3 .claude/hrms/scripts/defects.py --set <ID> fixed --note "<الدليل>"
```
السكريبت يرفض الإغلاق بلا دليل. اكتب فيه: رقم commit، مسار ملف الاختبار، أو المخرَج الفعلي.

## نموذج تقرير الإصلاح
لكل بند تُغلقه، أعطِ هذه البنود الستة مختصرة:
```
البند:        <ID> — <العنوان>
أُعيد إنتاجه:  نعم / لا (والسبب)
الجذر:        <أين كان فعلا>
بنود أخرى بنفس الجذر: <IDs أو "لا يوجد">
الكنس:        الأدوار ✓ · الشركتان ✓ · مسارات الوصول ✓ · اللغة ✓ · الحالات ✓ · الطبقات ✓
الدليل:       <commit / ملف اختبار / مخرَج>
```

## ما يبطل الإغلاق
- الإصلاح في CSS أو Frontend لمشكلة أمنية أو خصوصية → **مرفوض** (انظر `CAT-06`)
- catch أو إخفاء لخطأ الخادم بدل إصلاحه → **مرفوض** (انظر `API-01`)
- اختبار على شركة واحدة فقط → **غير مكتمل**
- «شغّال عندي» بلا خطوات قابلة للتكرار → **غير مقبول**
